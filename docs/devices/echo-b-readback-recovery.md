# ECHO-B 保存后读回失败：案例与修复

2026-10-29。此记录解释为什么旧版 CLI 退出失败不能直接理解为“尚未写入”，以及代码如何避免重复该错误。

## 观察到的事实

原始默认预设的一次操作先因 `Open: 0xe00002e2` 无法打开设备而终止，确实未写入。随后两次运行却都已收到全部 56 条写入 ACK（含保存），仅在 `after-metadata.jsonl` 读到 2–3 条时遇到 `GetReport: 0xe00002d8`。对话将这两次错误误报为“写入前失败”。

证据：[第一次完整写入的 ACK](../../runs/20261029T160620.070136Z-original-default/write-log.jsonl)、[再次执行的 ACK](../../runs/20261029T160645.859232Z-original-default/write-log.jsonl)。后一次的写前采集已经与最初默认备份相同；之后本对话的写前采集也相同，证明之前已经恢复了默认运行 EQ。

后续操作同样在保存后读取阶段遇到暂未就绪；只重新读取即可验证全部参数和系数与初始备份逐字节一致。[完成读回的验收](../../runs/20261029T160733.896197Z-original-default/verification.json)

`0xe00002e2` 在 macOS IOKit 中为 `kIOReturnNotPermitted`，`0xe00002d8` 为 `kIOReturnNotReady`。保存后短暂忙碌是与观察一致的解释，但没有固件内部证据证明具体原因，也不把它当成设备永久故障。

## 旧实现的问题

`preset.py` 在写前和写后都调用同一个探测程序，错误输出没有区分阶段。原生探测仅等待 20 ms 后读取一次，暂未就绪就退出；调用方又未根据 ACK 与运行记录核实设备是否已经改变。重新执行整个 `apply` 会再次写入已经生效的配置。

## 修复行为

- 原生探测只对暂未就绪重试 GET_REPORT，最多 20 次；不重新发送该查询请求，不吞掉权限错误或坏回包。恢复时在 stderr 记录读取次数。
- Python 管理层仅在探测器专用退出码 4 时，有限重启只读采集；每次尝试和诊断单独保存，成功后再生成标准采集文件。
- 原生写入器对 ACK 进行有限轮询，可等待暂未就绪恢复，但从不重发可能已经生效的写入命令。
- `status.json`、`events.jsonl` 与终端阶段提示区分 `not_written`、`write_uncertain`、`saved_unverified`、`saved_verified`。成功必须同时具有完整 ACK 和匹配的读回证据。
- `verify RUN_DIR` 校验历史计划完整性后，仅重新读取并比对，在 `checks/` 留下独立记录；不重新计算 EQ、不写入、不覆盖旧失败记录。
- `apply` / `verify` 使用协作锁避免本工具同时操作设备。外部 App、底层程序和 SIGKILL 等仍需结合记录判断，不能承诺自动回滚。

使用、退出码和超时边界见[仓库操作指南](../operations.md)。

## 本次验证范围

`make test` 覆盖 Python 的保存后暂未就绪恢复/耗尽、写前失败、权限错误、部分写入、缺少保存 ACK、写入超时、读回不匹配、只读复核、坏回包、历史计划篡改及并行锁；原生 C 直接对生产查询与 ACK 函数注入 11 种场景，验证重试次数与不重发行为。全部使用模拟设备 I/O。

首次新 `verify` 命令的实机只读检查未找到 ECHO-B，已如实输出 `readback_failed`，没有写入操作。记录位于 [无设备检查状态](../../runs/20261029T160733.896197Z-original-default/checks/20261029T161807.050883Z/status.json)。

同日设备重新连接后，新命令成功核对原始默认状态：[正常实机只读验证](../../runs/20261029T160733.896197Z-original-default/checks/20261029T162736.347995Z/status.json)。随后写入原始音色加额外 −12 dB 衰减，全部 56 条 ACK（含保存）成功，但写后采集遇到不同错误 `0x10000003`，因此准确保留 `saved_unverified`。没有重复写入，仅再次运行 `verify` 即核对通过：[写入状态](../../runs/20261029T162816.528160Z-original-default/status.json)、[后续验证](../../runs/20261029T162816.528160Z-original-default/checks/20261029T162828.601904Z/status.json)。

这些记录证明正常实机读取与“保存后报错、只读复核”流程有效，尚不能证明 `NotReady` 自动恢复的实机表现；也未进行本次配置的物理拔插测试。未将新错误归为 `NotReady` 或扩大自动重试范围。
